# The FR3 profile: one home for the robot's facts (config single source, step 1)

Operator instruction 2026-10-06: one source of truth for configs. Plan: `Control/docs/status/2026-10-06-config-single-source-plan.md`.

`robots/fr3/` states the Franka Research 3 once: `description.yaml` (joints, finger joints, TCP frame, URDF, factory torque ratings,
motor and render names), `gains.yaml` (default stiffness/damping, with the kd sweep that justifies it), `execution.yaml` (the admission
policy: THE statement of the FR3's speed and acceleration limits) and `sim.yaml` (the single-model MuJoCo plant). The example configs
include them and state only example choices; the project's configs include them in step 2.

Behaviour that follows from one statement:
* **Speed limits.** The console's planner times plans at the execution policy's limits when it states none (`planner_speed_limits`), and a
  planner limit above the policy is refused at load (it used to plan at 0.5 rad/s / 1.0 rad/s^2 and the supervisor's admission at
  0.4 / 0.8 refused the plans). The example robot now carries the FR3 policy, so the stock in-process console enforces it too.
* **Mode profiles include.** `ARM_CONTROL_MODE_CONFIG` is loaded with the config-tree loader, so a mode can include a shared one.
* **One description of the arm in both plant modes.** The single-model MuJoCo plant now applies the arm's reflected rotor inertia
  (`ARM_ARMATURE` 0.1, Franka's published MJCF value) that the scene-mode plant always had. That was the root cause of the FR3 wrist
  instability behind the 0.5 ms decision: without it a move left a 0.05 rad/s limit cycle on joint 7 even at 0.5 ms and the console's
  settling check failed in both the stock and the supervised graph; with it the arm settles to ~1e-6 rad/s, and both graphs complete
  their moves (verified live, headless). The 0.5 ms step stays (operator decision).
* **Slew per RT tick.** The servo law's torque slew (1 N*m) is applied per plant step; it is now scaled by step/1 ms, so the twin slews at
  the RT server's 1000 N*m/s at any step (at 0.5 ms it had slewed twice as fast).

Checked: `tools/inspect/config_snapshot.py` (parent repo) shows only the intended resolved-config changes (the example robot gains the FR3
execution policy; the example planner's 0.5/1.0 is gone; `sim_supervised.yaml` no longer restates a policy); the moved description,
gains and sim keys resolve identically. Benches: `check_sim_supervisor.py` (armature applied, slew per step), `arm_console --self-check`
(planner limits follow the policy).
